# 14 · Model transport and context economy

## Outcome
A run spends its tokens on new work. The request a model receives only grows between explicit compaction points, most of its input is read from the provider's cache, and a result stays in view until the request needs the room.

## Evidence that motivates it
The first real audit to reach its report used 533,093 tokens in 20 model calls. Of 61 tool calls, 26 (43%) recovered text the agent had already read, because a read is archived two turns after it arrives even when the request is far below its limit. Of 495,777 input tokens, 27,136 (5.5%) were read from cache: every call is a new CLI process that receives the whole history as one prompt, the projection rewrites earlier messages on each turn, and the pressure notice edits the system prompt. For comparison, one vendor reports 98% of its production input read from cache for an append-only harness (its own figure, not independently verified). The gap is cost and latency paid on every call.

## Built so far
- *Batches.* The recoverable archive works between a high mark (60% of the input ceiling) and a low mark (40%), both configuration. The plan is replayed from the durable messages on every call, so it keeps no state. Last resorts are unchanged.
- *Stable prefix.* The pressure notice is the last message of its request; the system prompt never changes within an invocation.
- *Measured by every bench run:* the recovery ratio and, for each turn with a previous request, whether it rewrote an earlier message and how much of the previous request it kept.
- *What the scripted bench shows.* An audit of six modules that fits its window: recoveries from 20% of tool calls to none, 21% fewer estimated tokens, and no request rewrites an earlier message (before, two of five did). An audit of sixteen modules that must compact: unchanged at 14% recoveries and 1% more tokens, because two protected turns of full-file reads and 20 KiB of instructions and tool definitions already sit at the high mark. The marks help where a conversation fits and do not hurt where it does not; a real model has not confirmed either figure.

- *Provider failures.* A failed model call is classified from its exception type, HTTP status or bridge code, never from its text: rate limit, overloaded, timeout, authentication, invalid request or other. The first three are tried again at most twice inside the reservation the call already holds, after 2 and 8 seconds or the provider's `Retry-After` when it is at most 30 seconds; a pause or cancel between attempts stops them. When retries are exhausted the failure leaves as `MODEL_RATE_LIMITED`, `MODEL_OVERLOADED` or `MODEL_TIMEOUT`, and the stage is not run again by the graph on top of them; `MODEL_AUTHENTICATION_FAILED` and `MODEL_REQUEST_INVALID` leave at once. The Claude runner names a rate or usage limit and an overload when the CLI's result says so. The Codex runner names what the pinned CLI reports for a turn that failed: a rate or usage limit, an overload, a session or access the provider refused, and a request it rejected. It reads the beginning of the CLI's own line, which states the status the CLI met, and never what the provider said after it; the native check holds each case against the pinned binary. Before, every failure of the provider behind that CLI ended as one generic process error that was never tried again, and a turn the CLI completed after reconnecting was discarded as an invalid answer; that turn is now kept. Every failed call leaves an execution event with its class and code. The Supervisor conversation retries the same way.

- *Provider caching.* Requests to the Anthropic API mark the end of the tool definitions, the end of the instructions and the end of the conversation, so each call can read what the previous one wrote; the marks are added after the reservation and the guard, which measure and check the request as the factory wrote it. OpenAI and Gemini cache a stable prefix on their own and are sent unmarked, and a CLI session manages its own cache. What a provider reports as read from and written to its cache reaches the ledger and is charged at its own prices ([15](15-observability.md)). Checked against the request the pinned integration builds, never against the provider: no cache hit has been observed.

- *Claude CLI transport.* A call to the Claude CLI used to send the whole prompt as one block, from a new temporary directory. The pinned CLI puts its cache point at the end of the request and names its working directory in what it writes itself, so every call wrote the whole prompt to the provider's cache and none could read it back. The prompt now goes as JSON Lines in blocks that only grow: a header that stays the same for a conversation (the instruction, the tools, the tool choice), then one block per turn (a message, and for an assistant message the tool results that answer it), with nothing to close after the last message; every call runs in the same empty directory; and the last block carries a cache point of the factory's own. The CLI lays a request out by model: for some its last cache point is the last block of the prompt, and for others, the default `claude-opus-5-5` among them, it is a message about the environment that the CLI adds after the prompt, so without the factory's own point the conversation would never end at one. With the CLI's points that makes at most four, the provider's limit, and the native check fails if a later CLI adds a fifth. Shown on the request the pinned CLI builds against a local stand-in for the provider, for the default model and for one of the other layout: a conversation that grew by a turn is sent as the same system, tools and blocks, byte for byte, plus one block, and the block where it ended before is a cache point of the earlier request. Nothing is kept on disk between calls; `--no-session-persistence` stays. Whether the provider then reads it from cache has not been observed: that needs a real run, which the ledger and Insights will show as the cache share.

- *Codex CLI transport.* A call to the Codex CLI ran in a new temporary directory. The pinned CLI writes its working directory, and the paths of its permission profile, into a message that comes before the prompt, so every call differed from the one before it ahead of the conversation, and a provider that caches a shared beginning had nothing of the conversation to share. Every call now runs in the same empty directory, removed afterwards. Shown on the request the pinned CLI builds against a local stand-in for the provider: for a conversation that grew by a turn, what the CLI writes before the prompt is the same on both calls, the identifiers it gives its own items aside; the prompt arrives as written, and the later prompt begins as the earlier one did up to where its conversation closes; from another directory, what comes first differs. Two limits stay. The CLI names a cache key of its own that is new for every process, and the factory has no setting for it. The date in the CLI's message changes each day. Whether the provider reads any of it from cache has not been observed.

- *Effort.* A model selection (the default, a role's, a specialist's, a flow phase's) can name a reasoning effort where the factory has read the provider's levels: today the two CLIs. The Claude CLI has low, medium, high, extra high and maximum, and takes the level as `--effort`. The Codex CLI has those and, below them, minimal and none, the levels the pinned OpenAI SDK declares, and takes the level as its `model_reasoning_effort` setting. Unset, the factory names none and the CLI decides by model. A role that names its own model never inherits the default model's level, as with cache prices, and the span of a model call records the level the factory named. Shown on the request the pinned Claude CLI builds against a local stand-in for the provider: with `claude-opus-5-5` each level arrives as asked and an unset one arrives as medium; with `claude-sonnet-4-6` an unset one arrives as high and extra high arrives as high; `claude-haiku-4-5` is asked for none whatever is named; and the level is the only thing that moves in the request. A saved level is therefore a request to that CLI, not a guarantee. The Codex CLI does the opposite: on the same kind of check, every level arrives as named for both layouts of its request, an unset one arrives as the CLI's default for the model (low for one of the two models checked, medium for the other), and the CLI checks nothing, so a level the model does not take is refused by the provider and the call ends as `CODEX_REQUEST_REJECTED`. Not built for the API providers: the pinned Anthropic integration sets adaptive thinking together with the effort, which changes more than the level, and the others were not looked at. What a level costs or buys in a run has not been measured, and neither has whether the provider keeps a conversation's cache across a change of level.

Still to build: a fallback model per role, effort for the API providers, the worker-session experiment and progressive skills. CLI session reuse is not planned unless a real run shows a low cache share with the block transport.

## Interfaces and behavior
**Archive under pressure, in batches.** A result stays in the model-facing request until the measured request crosses a high-water mark (initially 60% of `context_input_max_bytes`). The oldest eligible results are then archived in one batch down to a low-water mark (initially 40%). Between batches the request is append-only: no earlier message changes. `keep_model_turns` still protects the most recent turns, the escalation chain of last resorts is unchanged, and receipts record each batch. Both marks are configuration with documented defaults.

**Stable prefix.** System instructions, tool definitions and the response schema are byte-identical for the whole invocation. Anything that varies per call (the pressure notice, budget status) travels as a trailing message, never as an edit to the system prompt.

**Provider caching.** API providers use their prompt cache: explicit breakpoints after the stable prefix and at the end of the stable history where the provider needs them, automatic prefix caching where it does not. The ledger and the spans record cache-read and cache-write tokens, and cost uses the provider's cache prices ([15](15-observability.md)).

**CLI transport.** One process per call with the full history. For the Claude CLI the history travels as blocks that only grow between compaction batches, so the provider's cache can read back what an earlier call wrote, without keeping a session. Where a pinned CLI can resume a session, an invocation may instead keep one and send only the new messages, starting a fresh session at each compaction batch; that is adopted only if a real run shows the block transport is not enough and the CLI's terms allow it.

**Provider failures.** A failed call is classified (rate limit, overloaded, timeout, authentication, invalid request, other). Retryable classes are retried with bounded backoff inside the same reservation; the rest stop as today. A role may name one fallback model, used only after retries are exhausted and recorded with the reason. Every failed call leaves an event with its class.

**Effort.** A model selection may set the provider's reasoning-effort level where the provider has one, so a role, a specialist or a flow phase with its own selection has its own level. The default leaves the provider's own default.

**Worker sessions: an experiment with a decision gate.** For the implement and repair stages, an alternative worker runs a vendor agent session inside the executor sandbox instead of SABRE's own tool loop: the agent keeps its own cache, compaction and parallel tool calls. SABRE supplies the task packet, enforces policy through the agent's tool hooks (path scope, denied operations, secret guard on outputs), caps turns and spend, records usage, cost and a transcript digest, and verifies the result with the same deterministic gates, review and security stages. It requires API-key authentication and an egress proxy that adds the credential outside the sandbox; it is never offered on a subscription login. It is adopted only if the evaluation suite ([16](16-evaluation.md)) shows a better pass rate or cost at equal safety. Until then it does not ship.

**Skills.** Skills stay inline while each is a few hundred bytes. Once a skill grows past a documented size it is listed by name and summary and loaded on use.

## Acceptance
On the long-audit bench task: recoveries are under 10% of tool calls, and on turns without a compaction batch the common prefix with the previous request is at least 90% of its bytes; both figures are reported by every bench run, with the scripted driver included. No archived result becomes unrecoverable, and receipts stay valid across a batch. The pressure notice never changes the system prompt. Cache tokens appear in the ledger, the spans and the run audit. Retries and fallback are tested for each failure class, including that a non-retryable class never retries and that a retry never reserves twice. A worker session cannot read outside its workspace, reach a destination other than the model proxy or see a credential, and a denied tool call is recorded.
