# Operations

## Configuration and access

Use `node bin/sabre.mjs init` to generate service-specific protected bootstrap files and a 32-byte master key. Existing installations use the migration command before restarting with the new configuration. Access credentials are created for this factory, not read from the owner's application homes. The ignored `.env` holds public configuration only; raw secret environment variables are rejected, including empty placeholders.

For the previous `.env` layout, build the current `postgres` and `api` images and run `node bin/sabre.mjs migrate-credentials`, followed by `up`. The migration quiesces only this factory's services, preserves bootstrap identities, imports integration values through standard input and confirms encrypted storage before atomically removing secret fields. An interrupted import reconciles only identical existing values; a different destination value requires explicit review. It never creates a plaintext configuration backup. `access-token` remains an explicit owner-terminal command for clients requiring a bearer token; the panel does not need it.

`node bin/sabre.mjs up` finishes by opening the panel; `node bin/sabre.mjs open` pairs a browser at any time. The launcher requests a sixty-second, single-use grant inside the API container, then starts a one-use relay on a random loopback port with an unguessable path. The platform opener (`explorer.exe`, `open` or `xdg-open`) receives only that relay address; the relay answers once with a redirect that carries the grant in the URL fragment, then closes. The grant never appears in process arguments, terminal output or logs, and the launcher does not invoke PowerShell or a shell. If the browser does not fetch the relay within sixty seconds, the command fails and nothing remains valid. `up --no-open` skips this step, and `CI` environments skip it automatically.

Pairing does not trust "local" callers. Containers such as the model runners can reach the published API port through the Docker gateway, so the API cannot distinguish them from the browser by address. Sessions are created only from launcher grants, which require the owner credential that stays inside the API container.

The browser removes the URL fragment before exchanging it for an HttpOnly, SameSite session. The session slides: each use extends it to `SABRE_PANEL_SESSION_DAYS` (default 30, maximum 90) after the last use, written at most once per hour, and it expires after that many idle days. Config → Access lists paired browsers by coarse label (for example "Chrome on Windows"; the full user agent is not stored) and revokes any other browser; revocation applies on that browser's next request. When the panel is not signed in, the tab checks again when it regains focus, so pairing from another tab or the launcher needs no reload. Mutations require the session-bound CSRF value; exact origin, host and fetch metadata checks reject other sites. Cookie authentication cannot access MCP or private service adapters. Logout revokes the session. Opening a new session in another tab may require reloading an older tab; a rejected mutation is never replayed automatically. `SABRE_PANEL_ORIGIN` must match the exact local origin, including port; it is not a remote-access switch.

Host tooling versions are declared in `web/package.json` and the lockfile; runtime images and Python dependencies are pinned in infrastructure and `backend/uv.lock`.

- `SABRE_BOOTSTRAP_FILE`: path to the protected file granted to that process. Control holds database URLs and service authentication; broker and gateway files each contain only their own adapter identity.
- `SABRE_VAULT_MASTER_KEY_FILE`: read-only master-key path, mounted only into trusted control processes. Loss of this file prevents decryption; a wrong or corrupt key fails startup rather than regenerating over existing data.
- `SABRE_MODEL_PROVIDER`: `codex_cli`, `claude_cli`, `openai`, `anthropic`, `google` or an explicitly configured `local` endpoint.
- `SABRE_MODEL_NAME`, optional `SABRE_MODEL_BASE_URL` for a local endpoint. Hosted providers use official destinations.
- `SABRE_ROLE_MODELS`: public JSON overrides for `supervisor`, `analyst`, `architect`, `developer`, `qa`, `reviewer` and `security`, using model names, providers, prices and capabilities. Secret values are forbidden. Unspecified roles inherit the same destination's default credential; an explicit empty `secret_ref` disables inheritance. Any nonempty reference must exactly match its derived destination identifier. A provider change is explicit configuration, never automatic failover.
- `SABRE_MODEL_INPUT_USD_PER_MILLION`, `SABRE_MODEL_OUTPUT_USD_PER_MILLION`, `SABRE_MONTHLY_BUDGET_USD`: mandatory paid-model accounting configuration.
- `SABRE_MODEL_CACHE_READ_USD_PER_MILLION`, `SABRE_MODEL_CACHE_WRITE_USD_PER_MILLION`: optional prices of cached input, also editable per model in Config and Agents. Providers count cached tokens inside the input tokens; with these set, tokens read from the cache and tokens written to it are charged at their own price and only the rest as input. Unset, cached tokens are charged at the input price. One write price covers every cache lifetime. The Anthropic API caches only what a request marks: the factory marks the end of the tool definitions, of the instructions and of the conversation with the five-minute lifetime, so set both cache prices for an Anthropic model. OpenAI and Gemini cache on their own.
- `SABRE_EMBEDDING_MODEL` and `SABRE_EMBEDDING_USD_PER_MILLION`: optional hybrid lexical/vector retrieval with OpenAI or the configured local provider; output dimension is 1536. Other provider credentials are not sent to an embedding endpoint.
- `SABRE_SLACK_OWNER_ID`: optional private Slack integration owner.
- `SABRE_OTLP_ENDPOINT`: optional local diagnostics endpoint (OTLP over HTTP). `SABRE_TRACE_VIEWER_URL`: optional address a trace opens at, an http(s) address with `{trace_id}` in it. `sabre up --traces` sets both for the bundled viewer when they are not configured.
- `SABRE_CONTEXT_DEDUP_ENABLED` (default `true`): master switch for invocation-local history projection. `SABRE_CONTEXT_ARCHIVE_ENABLED` (default `true`) lets older internal read responses of at least 2 KiB become recoverable references, including unique reads, when the agent is authorized to use `read_context`. They leave in batches: nothing leaves while the complete request is below `SABRE_CONTEXT_ARCHIVE_HIGH_WATER` (default `0.6` of the input ceiling), and a batch takes the oldest down to `SABRE_CONTEXT_ARCHIVE_LOW_WATER` (default `0.4`). Higher marks keep more in view and make more requests append-only, which a provider's prompt cache rewards, at the price of larger requests where nothing is cached. `SABRE_CONTEXT_DEDUP_KEEP_MODEL_TURNS` defaults to 2 and normally protects recent turns. Only if the complete request still exceeds its input ceiling can recent successful internal reads also become exact recoverable references. Instructions, actions, arguments, failures and recovery pages remain intact. With archive mode off, legacy identical-read dedup uses `SABRE_CONTEXT_DEDUP_TRIGGER_BYTES` (65536) and `SABRE_CONTEXT_DEDUP_MIN_RESULT_BYTES` (4096). Disabling projection does not remove the recovery tool needed by a pending checkpoint.
- `SABRE_CONTEXT_INPUT_MAX_BYTES` (default 98304): application ceiling on the complete measured request, including system instructions, tools and the structured response schema. An irreducible request blocks before a model reservation. This is a byte ceiling, not an exact tokenizer or a guarantee about the CLI's internal requests.

After owner authentication, open Tools, choose the service's tab (GitHub, MCP servers or Notifications) and use the connection's own button to add or replace its credential; model provider credentials are in Config › Models. Destinations remain restricted to the server's catalog. Values are write-only: the UI clears its input after success or failure and only lists configured state, revision and update time. Create/update/deactivate operations use revision checks; refresh after a conflict rather than overwriting another editor. Credential deactivation removes the stored ciphertext but does not revoke the upstream token. The gateway closes an old Slack connection on its next ten-second credential check.

GitHub and MCP connections have independent enabled states stored with revision checks and audit events. Disabling a connection blocks subsequent call boundaries; a request already sent can finish. This switch does not delete its credential or authorize tools for another project.

In Tools › MCP servers, add a named public HTTPS endpoint on port 443. Saving always disables it. Configure its write-only credential from the server's row when needed, discover its bounded manifest, then assign individual tools to roles and save. Each approved tool binds its name, description and input schema by digest; a changed manifest requires review before use. Only read tools are supported in this initial adapter: restrict the remote credential to read scopes as well, because a manifest cannot prove the server's behavior. Choose project access separately while that project is idle, then explicitly enable the connection card. Updating an endpoint gets a new credential destination and clears the panel's tool selection. Static instance connections remain read-only in this editor; private/local MCP endpoints require explicit instance configuration. Network connections pin validated public DNS results while retaining the original TLS hostname and certificate verification, without redirects, proxies or automatic OAuth.

Projects (a page of the Runs area) registers, edits and archives projects. An edit replaces the name, base branch, environment, verification commands and browser preview together and carries the revision it was read at; it is refused while a run of the project is executing and applies to runs launched or resumed afterwards. Archiving takes a project out of every list, picker and the daily security report and refuses new or resumed runs for it, while its runs, memory and evidence stay; it is refused while a run is queued, running, paused, blocked or waiting, and the refusal names the run. Restore reverses it. Each change records its revision, its action and the names of the fields it changed. The console offers no deletion.

**GitHub connection.** Tools › GitHub › Connect GitHub registers a private GitHub App for the factory on your personal account or on an organization you name, and returns to the console; nothing is pasted. You then choose on GitHub the repositories the app may use. The app's private key and client secret are stored in the vault and never shown. Once the app is installed, reading and delivering stop using `github.read` and `github.publish` tokens: each operation asks GitHub for a short-lived token for one repository with only the permissions it needs, kept in memory and never stored. Delivery commits made through the connection carry no author of their own, so GitHub signs them as the app, which a repository that requires signed commits accepts. Disconnect removes the app's credentials from the factory and changes nothing on GitHub: uninstall or delete the app there. Creating repositories still uses the `github.create` token. The flow must be completed within one hour from a paired browser; a step that fails leaves no credential behind, and if GitHub registered the app without the factory receiving its key the message says to delete it on GitHub and connect again. This has been exercised against a synthetic GitHub only.

GitHub discovery lists public repositories for a username and authorized repositories for an organization. Private access uses only the dedicated `github.read` credential; publication credentials are not reused. Import rechecks the canonical repository and branch, then registers the chosen profile and verification commands without starting an order. Creating, deleting or changing visibility of remote repositories is not supported by this discovery operation.

A project is added in one place, Runs › Projects › Add project, from three sources: the repositories GitHub access reaches (those of the connection once the app is installed, an account search while only tokens are configured), a repository address, or a new repository. Tools › GitHub keeps the access and links there.

Add project › New repository stores an immutable proposal with owner, name, visibility (private by default) and description. Review those exact details before approving. Approval and queue admission commit together; the maintenance worker claims the operation before making its single creation attempt. A lost response enters reconciliation rather than repeating the POST. A repository observed by name without a valid receipt remains unconfirmed. Proposals and decisions survive disconnects and can also be queried by id through HTTP or MCP. The created repository is empty (`auto_init=false`); its first commit and registration as a project are separate actions.

Use separate least-privilege GitHub credentials for repository reads (`github.read`), branch/PR publication (`github.publish`) and owner-approved creation (`github.create`). Creation requires the upstream Repository creation or Administration write permission; existing Contents/PR tokens do not imply this grant. SABRE never falls back to another destination. Model identifiers include their provider; local and external MCP identifiers include the endpoint digest. Changing provider or endpoint never redirects an existing key. Old destinations remain visible and removable, but require the corresponding public configuration before replacement. Raw values never become agent memories or credential tools.

Usage reserves conservative token/cost bounds before each request. The input reservation estimates tokens from the sent bytes at 2.5 bytes per token (code, JSON and English average about 4), plus 2,048 tokens for API providers or 16,384 for CLI runners, which add their own instructions and tool definitions; settlement replaces the estimate with the reported count, and a CLI turn that exceeds its reservation still stops. One call at the 98,304-byte context ceiling therefore fits the default 100,000-token budget. Missing acknowledgements retain reservations because the provider may already have billed the request. The account's actual invoice remains authoritative. Local providers must pass the same tool and structured-output capability checks; changing a provider does not authorize sending data to another destination.

Context projection retains full LangGraph history and saves guarded original read responses, older `execute` results and the `content` of answered `write_file` calls as immutable artifacts before replacing their model-facing content. An archived command result keeps its exit code visible; when its output was bounded, the reference also names the complete output (`output_digest`), which `read_context` pages back as well. An archived write keeps its tool, call id and path; only the content becomes a reference, in every provider-native copy of the call, and `write_file` rejects a copied reference as content with a recoverable `CONTEXT_REFERENCE_CONTENT` error. `read_context` recovers exact historical text in pages of at most 8,192 Unicode characters, authorized from this child's original message/call pairs. Authority is restored before a pending tool can run after restart. The complete original passes the current secret guard before any page is returned. A recovered page is itself replaced by its coordinates once it is older than the protected turns, so restoring history adds a reference per turn instead of a page. Agents are told how long results stay in view and to record what they will rely on with `record_note` before moving on. A conversation that still does not fit after everything recoverable is archived loses its oldest read-only turns from the view, never a write, a command, a note or an error; from 85% of the input limit the agent is told to stop exploring and return its result. `CONTEXT_BUDGET_EXHAUSTED` now means that instructions, effects and the protected recent turns alone exceed the limit. References never establish current file contents; edits still require the current source digest. Errors, other tool arguments and human decisions are not archived by this policy.

Each new model reservation atomically stores a content-free context receipt in the existing usage ledger: policy, child scope, original/sent request digests and byte counts, read-response references and measured retrieval coverage. Settlement preserves it. The work audit shows aggregate coverage and bytes without exposing prompts or outputs; older calls remain unmeasured. OpenTelemetry exports only numeric projection counters. Codex JSON puts stable instructions and tool contracts before changing conversation content, preserving the decoded request; prefix reuse is an opportunity, not proof of cache hits or subscription savings.

Specialists receive a task packet with bounded completed dependencies and a verified path/digest delta from the intake source index. Legacy checkpoints without that index report an unavailable delta. Approved project memory is selected for the task and source commit: at most four excerpts and 6 KiB, with complete provenance and explicit omissions. `read_memory` rechecks scope, activity, invalidation and original digest on every bounded read. Initial memory excerpts and historical memory reads are revalidated before subsequent model calls and before resuming pending tools; invalidated, changed or unidentifiable legacy references block with `MEMORY_CONTEXT_CHANGED` rather than silently reusing stale knowledge. Replan with the current approved context or explicitly restore a valid memory before continuing. Empty memory neither advertises the read tool nor invokes embeddings. Memory excerpts and dependency summaries remain untrusted observations. The developer's `edit_source` applies exact replacements with a current digest and occurrence count; the broker performs comparison and write under its workspace lock, rejecting concurrent/stale edits.

Historical replay can compare request bytes and token estimates without invoking a model, but does not establish functional quality or paid savings. Account for extra recovery calls and cache behavior before attributing an improvement. Existing usage reservations, unknown consumption and blocked orders are never reset by context policy changes.

The owner can increase a paused or blocked order's token ceiling or its model-invocation ceiling from the console. Over MCP, `sabre_increase_token_budget` and `sabre_increase_call_budget` file the same change as a request that the owner confirms in the console (see [Owner confirmations](#owner-confirmations)). Supply the plan revision, expected current limit and a higher limit; the authenticated API provides the same commands. A stale revision or limit is rejected, and the audit event records both limits atomically. Each command changes only its specified ceiling. It does not resume the order, authorize API spend, change active-time limits or reset usage. Resume retains the plan and child history while using the authorized ceilings; unknown reservations remain counted. Agents and the Slack conversational gateway cannot grant these increases. These two commands, and `sabre_use_cli_progress_limits`, apply only to an order without a budget policy. An order with a policy, which includes every run launched from the console, takes `sabre_amend_budget`; asking for a flat-limit change on it is refused when the request is filed (`VERSIONED_BUDGET_REQUIRED`), so the owner is never asked to confirm a request that can only fail.

New orders use independent token, invocation, active-time and repair policies: choose a bound, an explicitly preauthorized finite reserve, or an uncapped cumulative metric. Zero API authorization never permits paid API work. Budget inspection separates measured consumption, unknown reservations, reserve activation and owner amendments. An amendment compares the budget revision and preserves the original policy and usage; reconciliation can retain a lost call's complete reservation as unknown before resumption. Subscription usage remains external to SABRE's API-cost ledger.

The older **Per-agent controls (CLI)** transition and `sabre_use_cli_progress_limits` (a request over MCP, like the other budget tools) remain compatibility operations for historical orders without a versioned policy. They require zero API authorization and spend, compare the prior plan and budget, and remove all three old cumulative caps together. New policies use metric amendments instead. Neither path resets consumption or checkpoints.

Each agent invocation retains LangGraph's 50-step limit and a ten-minute deadline. Exhaustion blocks with `AGENT_STEP_LIMIT` or `AGENT_TIMEOUT` for inspection. Individual CLI calls retain their two-minute deadline and bounded output; tools keep their own timeouts. Repairs default to two but follow the run's explicit policy. Three consecutive identical gate, source-snapshot and task fingerprints trigger a no-progress intervention by default, even when repairs are uncapped. Delivery still requires QA, deterministic gates, technical review and independent security. Human decisions, cancellation, missing scanner results and permission/configuration errors remain stopping conditions. CLI aggregate token consumption may only be known after invocation; the panel does not promise an exact preventive token cap.

API, compatible-endpoint and embedding calls cannot borrow this authorization: work reservations without a verified CLI receipt require explicit cumulative quotas. A later provider change to an API blocks before sending rather than silently running without a budget. Existing bounded orders retain their limits; cumulative-limit increase commands reject an already unbounded CLI policy instead of resetting it.

### Model providers

An API provider (OpenAI, Anthropic, Google or a local OpenAI-compatible endpoint) is configured entirely in Config › Models: choose it, store its key in the write-only field and name an explicit model. It is the path for anything shared or run for others. The two CLI runners below are an alternative for the owner's own machine: each signs a vendor's CLI in with a personal account, inside its own isolated container. Whether a plan allows that use is for the owner to check with the vendor.

### Codex subscription runner

For an existing installation, run `node bin/sabre.mjs prepare-codex`, build `api` and `codex-runner`, set `SABRE_MODEL_PROVIDER=codex_cli` in `.env`, and run `up`. Select an explicit model name in Config › Models before launching a flow. Run `node bin/sabre.mjs codex-login` in the owner's terminal and complete the official device flow. Authentication lives in a dedicated protected volume. Neither setup nor SABRE reads the owner's interactive Codex home. The runner has no Docker socket, project mounts, database credential, GitHub credential or vault master key. Only the control services share its private bridge token.

SABRE still owns the LangChain tool loop and LangGraph checkpoints. The pinned CLI runs with isolated configuration, a read-only sandbox, native shell and image tools disabled, no configured external MCP servers, bounded input/output and a two-minute invocation timeout. Its structured result requests tools from SABRE's role-scoped catalog. The native-policy check uses the actual pinned binary against a synthetic provider with no credentials or external network: `node infra/dev.mjs codex-policy`.

Each runner admits only one model invocation at a time. Admission can wait up to twelve seconds for an existing session-status check; that wait, login check and inference share the same two-minute deadline. Monitoring cannot start another status process while an invocation is admitted. The adapter preserves allowlisted runner error codes with local messages, never the remote error body. It does not automatically retry a model request or release usage reserved for an unknown outcome.

The native runner has separate digest-pinned Linux amd64 and arm64 binaries. Native checks select architecture-specific syscall numbers; passing a build is insufficient to establish host isolation. It uses `infra/codex-seccomp.json`, derived from [Moby seccomp v0.2.4](https://github.com/moby/profiles/tree/245180c51918481c0525424b3ee025d2b435d46c/seccomp) with scoped namespace and mount calls required by [Codex 0.164.0's bundled bubblewrap 0.11.2](https://github.com/openai/codex/tree/6aaac694803004a63c6f393d153c96d22521a6b9/codex-rs/vendor/bubblewrap).

Run the native-policy check before connecting an account on a new host. Host security modules also mediate these calls: Docker's default [AppArmor profile](https://docs.docker.com/engine/security/apparmor/) denies mounts even when seccomp permits them. A failed positive control means the sandbox is unavailable on that host; it is not evidence that private-file isolation works. Local setup does not install host policies or disable security modules.

The GitHub-hosted Ubuntu CI job uses `infra/codex-apparmor-ci.sh` to compile and load a uniquely named profile for its native-test container. The profile retains Docker's other restrictions and permits the bounded namespace mounts needed by the pinned helper; a separate destination check proves AppArmor still denies other mounts. The wrapper removes its consumers before unloading its exact profile and fails if cleanup is incomplete. It does not change `docker-default`, daemon configuration or sysctls, and refuses ordinary local execution. This CI policy is not an automatic deployment policy for other hosts: their administrator must review compatibility and run the full native suite with the effective deployment configuration.

The operations helper verifies the profile digest. The local Docker client reads the absolute checkout path on Windows, Linux and macOS. The profile is not mounted into the runner, and the launcher does not change host policy. `node infra/codex-profile-check.mjs` verifies actual Compose transport, exact 64-bit values and noninteractive execution. Native checks cover allowed workspace reads, denied credential reads and syscall variants with UID 10001, a read-only root, zero outer capabilities and `no-new-privileges`. Never round the profile through JavaScript JSON parsing.

Codex and Moby use Apache-2.0; bubblewrap uses LGPL-2.0-or-later. Original licenses and notices are retained in `infra/licenses/` and the runner image under `/usr/share/licenses/sabre-codex/`; the immutable source links above identify the corresponding upstream code.

The call counter counts adapter invocations. A CLI invocation can make multiple internal provider requests, and aggregate token use is only known afterward. SABRE records returned tokens and retains reservations on an unknown result. For orders with cumulative quotas, it stops before dispatching requested tools when usage exceeds its reservation. This is not an exact preventive token limit or a subscription quota meter. CLI usage records zero API spend; zero API authorization does not permit paid API calls. Subscription charges and account limits remain external. Embeddings require their own supported API configuration; CLI mode can use lexical memory without them.

### Claude and model selection by role

Run `node bin/sabre.mjs prepare-claude`, build `api` and `claude-runner`, then run `up`. `node bin/sabre.mjs claude-login` must run in the owner's terminal to complete the official Claude login; it restarts the bridge after the temporary login container has exited and been removed. A bridge that serves no account, which is what `up` starts after preparation, is stopped by the login itself, so the first login needs no other step. A bridge with a subscription connected is never replaced implicitly: stop it with `node bin/sabre.mjs stop claude-runner` before changing its account. It creates a factory-owned session without importing the owner's existing CLI credentials. Preparation enables the public Claude profile for subsequent starts; selecting a provider in the panel does not start containers or authenticate an account. Run `node infra/dev.mjs claude-policy` before connecting an account on a new host.

This adapter supports verified personal Claude subscriptions only (Pro, Max or Ultra). Other account types, an unknown subscription type or a cached organizational policy block inference; they are not silently downgraded to an API key. The proprietary CLI is downloaded from Anthropic with a pinned version and digest; its publisher notice is retained separately from SABRE's source license. See the official [CLI reference](https://code.claude.com/docs/en/cli-reference) and [authentication guide](https://code.claude.com/docs/en/authentication).

Claude uses the CLI's JSON Schema output contract and accepts only its validated `structured_output` envelope. The internal `StructuredOutput` formatter has no filesystem, shell or MCP capability. The instruction explicitly separates this formatter from SABRE's action array and its `tool_choice`. Operating tools remain absent; a wildcard tool deny is not used because it also denies this formatter. A maximum of two internal CLI turns allows one formatting continuation within the same two-minute invocation deadline, as the [structured-output contract](https://code.claude.com/docs/en/agent-sdk/structured-outputs) can re-prompt after a schema mismatch. Usage sums every internal request; this does not add a SABRE tool loop or retry a failed invocation. Missing or invalid structured output, turn exhaustion, denied native actions and invalid usage are distinct local errors; raw provider bodies are not logged or returned. There is no fallback that extracts an action from prose or relaxes the schema. Successful messages identify `claude_lines_v1` in their response metadata. Unknown reservations from earlier protocol failures are retained.

The prompt reaches the CLI on standard input as one user message of several text blocks: a header that does not change during a conversation, then one block per turn, in JSON Lines with nothing to close at the end. A conversation that grew is therefore the same blocks followed by one more, which is what lets the provider's cache read back what the previous call wrote; the CLI marks the last block as its cache point. Each call runs in the same empty directory, removed afterwards, because the CLI names its working directory in every request. No session is kept between calls. The bridge and the control services change together: after an update, build both `api` and `claude-runner`, since a control service of one version and a bridge of another refuse each other's requests.

Open **Config › Models** to choose the default, and **Agents** to set the overrides for supervisor, analyst, architect, developer, QA, reviewer and security. Unchecking inheritance starts an explicit override. Confirm the displayed destinations before saving; CLI destinations identify private bridges to the corresponding external provider. API credentials remain write-only in the model connection and destination-bound. Changing a model does not raise work-order budgets or resume blocked work. Conflicting edits require refreshing the saved revision; an in-flight configuration change may require explicitly resuming the interrupted order.

For a heterogeneous trial, keep the task, acceptance criteria, gates and limit policy fixed, including cumulative ceilings when enabled; record the baseline ledger before resuming, and compare the new measured tokens, unknown reservations, elapsed time and outcome by role/provider/configuration revision. Claude input accounting includes ordinary input, cache reads and cache creation exactly once. A completed single mixed-provider order establishes operability, not a causal quality or savings comparison; comparable repeated orders would be needed for that claim. Keep the original ledger and checkpoints when limits are reached.

In bounded orders, embedding lookups consume the order's call, token and USD limits as well as the global monthly limit. CLI progress mode rejects work-order embedding reservations before sending. Direct owner queries and memory proposals use the service limit and the same monthly limit. The repair lesson proposed after a delivery is stored lexically without a paid embedding request. Recovering this post-delivery step and the workspace cleanup has a separate sixty-second control timeout; it cannot restart agents or project code after the execution budget expires.

Changing provider in a role override requires that provider's explicit credential; it does not inherit another provider's key or endpoint. Custom endpoints are accepted only under the explicit `local` configuration. Model providers use LangChain's maintained OpenAI, Anthropic and Google packages, with no automatic provider fallback.

## Owner Supervisor conversation

The persistent Supervisor control is available throughout the authenticated panel. Choose the factory context for coordination or a specific run for scoped supervision. The control worker processes replies independently of the work queue; paused runs do not close their conversations. A provider must still be connected and an explicit model configured: while the factory reports that the Supervisor's role has no model it can call (no provider connected, no model chosen, or a CLI session that is not signed in), the control reads **No model** instead of Ready and links to Config › Models. A message sent before that is kept and stays blocked until you resume it. Conversation inference uses the existing separately bounded chat allowance and monthly spend policy, not an automatic increase to a run budget.

Messages default to read-only. Grant specific action tools for each message when you want the Supervisor to act. Run-scoped messages cannot start another run, register projects or modify other runs. No conversational grant can increase budgets, waive security controls, merge or deploy. Positive API-spend authorization for a new run must be explicit in the owner message. An advisory warning stays in the conversation unless an authorized tool changes the run; it is not automatically injected into an in-flight worker's context.

A conversation keeps its whole history, but each model request is bounded. When the history no longer fits, the oldest complete turns are left out of that request, never a tool call without its result, and the Supervisor is told how many messages were omitted so it reads current state with its tools. Only a single message whose own tool results exceed the bound is refused with `CONTEXT_BUDGET_EXHAUSTED`.

Admission and worker enqueue commit together, with a stable message request key. History survives navigation and service restarts. If a response is uncertain, reconcile the recorded message before submitting a new request. A blocked message can be explicitly reconciled and resumed with its original identity and action grants; it cannot acquire new permissions during resumption. A rate limit, an overloaded provider and a timeout are tried again twice inside the same reservation; a failure that persists, and the three-minute conversation timeout, are displayed as blocked states that name the kind of failure, with unknown inference reservations retained. Starting a new message does not silently recover an older incomplete checkpoint.

The owner MCP exposes `sabre_talk_supervisor`, `sabre_supervisor_messages` and `sabre_resume_supervisor_message`. These tools are owner-authorized capabilities. They must not be used as a substitute for scoped delegated-client authentication. The existing Slack gateway credential cannot call the owner conversation HTTP endpoints.

This feature introduces migration 5. Back up before upgrading and retain the exact previously running images and protected bootstrap/master volumes. Returning to a runtime that only understands migration 4 requires restoring its matching backup; do not point that older runtime at the upgraded database.

## Operating from the terminal

`sabre runs [--state active|attention|closed|all]` lists runs; `sabre run <run>` shows one with its usage, pending questions (current revision only) and tasks; `sabre watch <run>` follows recorded phase, agent and tool events until the run settles. `sabre ask "<message>" [--run <run>]` sends a read-only message to the Supervisor and prints its reply. `sabre answer <run> <question> "<answer>"` records an answer; `sabre pause|resume <run>` and `sabre cancel <run> --yes` control a run. Runs and questions accept a unique prefix or suffix of their identifier. These commands call the same MCP tools as the console through the in-container client: the owner credential never reaches the host, arguments or output. `access-token` is deliberately not a `sabre` command; it remains a terminal-only `node infra/ops.mjs` action.

## MCP access

The authenticated Streamable HTTP endpoint is `/mcp/`. Register that endpoint and its bearer-token environment variable through the client's supported configuration UI. No setup helper edits the owner's Codex home.

For local operation, `node infra/mcp.mjs tools` lists the current catalog and `node infra/mcp.mjs sabre_list_work` queries work. Invoke other tools with `node infra/mcp.mjs <tool-name> work/arguments.json`; the file contains the tool's JSON argument object, including `request` when its schema requires that wrapper. The official MCP client runs inside the API container and reads its authentication there; no token is copied to the host or printed. Inputs are limited to 64 KiB and output to 1 MiB. A timeout never triggers an automatic retry: reconcile the work or project before repeating a mutation. Pending questions use the explicit answer tool when native elicitation is unavailable.

Core tools include `sabre_submit_work`, `sabre_get_work`, `sabre_list_work`, `sabre_answer_question`, `sabre_control_work` and `sabre_change_scope`. Submit returns a durable id immediately. Read pending questions from `sabre_get_work` and answer a clarification with its `question_id` and `plan_revision`. The same question can be answered in the panel; subsequent answers are rejected. Owner decisions (architecture, permission, scope and exception questions) are not answered over MCP: see [Owner confirmations](#owner-confirmations).

MCP clients differ in support for native elicitation and long-running task extensions. The durable work-id and question tools remain the compatibility path. SABRE does not promise unsolicited chat messages on hosts that cannot receive them.

`sabre_resolve_question_native` offers native owner elicitation when supported. Declining or cancelling that prompt leaves the decision pending. It cannot resolve a question from an earlier plan revision.

### Docker access

Only the `docker-proxy` service mounts `/var/run/docker.sock`. It has no network and listens on a Unix socket in the `docker-proxy` volume, which the executor mounts read-only and uses as `DOCKER_HOST`. The images, internal networks and scanner volumes the executor may use are declared once in `infra/compose.yml` (`x-executor-docker`) and read by both services, so a new sandbox image or network needs no second edit. A request outside the policy returns `403` with a `SABRE Docker policy:` reason, and the proxy logs the reason without the request body. `node infra/runtime-check.mjs` fails if any other service holds the socket or if the executor can inspect the API container, list unowned containers or read a credential volume.

### Owner confirmations

An MCP client acts with the owner's authority but is not the owner, so budget changes, security exceptions, answers to owner decisions and repository creation are not applied over MCP. `sabre_increase_token_budget`, `sabre_increase_call_budget`, `sabre_use_cli_progress_limits`, `sabre_amend_budget`, `sabre_reconcile_budget`, `sabre_approve_security_exception`, `sabre_propose_answer`, `sabre_propose_repository_approval` and `sabre_launch_create` file a request and return it as `pending`. `sabre_command` refuses budget payloads, `sabre_answer_question` and `sabre_resolve_question_native` refuse architecture, permission, scope and exception questions, and `sabre_decide_repository` only rejects. A Supervisor message that arrived over MCP cannot record an owner decision either, even when it quotes the answer. Nothing changes, and for a run a run event tells the owner that a request is waiting. `sabre answer` in the terminal follows the same rule: it files the answer to an owner decision and says so.

The console signals the request in every section without moving the page: a short notification announces it once per browser, and the Supervisor launcher shows how many items wait (amber) or that a decision did not take effect (red). The request is decided in the Supervisor inbox, which lists it with its exact fields. A decision the factory refused, or whose outcome is unknown, stays in that inbox until the owner dismisses it; a reload does not repeat what was already announced or dismissed. The same notifications report a run that completes, fails, blocks or asks a question while the console is open. Only a paired browser can confirm or reject it: `POST /api/v1/confirmations/{id}/confirm` and `/reject` refuse the owner bearer with `CONSOLE_CONFIRMATION_REQUIRED`, and the decision must carry the digest of the request that was displayed. Confirming runs the same operation as the console, with its revision checks, at most once. An operation the factory refuses is recorded as `failed` with its code; if the outcome cannot be established the request stays in `applying` and is never retried. A request not decided within 24 hours expires. At most 20 requests wait at a time, and filing the same request again returns the pending one.

`sabre_confirmations` and `sabre_confirmation` read the state of a request; no MCP tool decides one. The gate covers the MCP surface, including the local bridge. A process that holds the owner credential itself can still call the HTTP API, so that credential stays inside the control container. Clarification answers, run submission, pause, resume, cancel and scope changes are not gated.

### Remote agents

Remote agents and chat clients never receive the owner credential. The owner issues a delegated grant with `POST /api/v1/delegations` (principal, projects, operations among `work.submit`, `work.query`, `work.answer` and `work.cancel`, expiry up to 24 hours, cumulative call, token, cost and time limits, and a run count). The bearer (`sabre_d_...`) is returned once and stored only as a hash; `GET /api/v1/delegations` lists grants and `DELETE /api/v1/delegations/{id}` revokes one.

The delegated endpoint is `/delegated/mcp/`. It accepts only an active delegated bearer, rejects the owner token and any browser `Origin`, and authenticates every tool call again, so a revocation or expiry applies to the next call. Its tools are `sabre_grant`, `sabre_list_projects` (granted projects only), `sabre_get_work` (runs this grant submitted) and `sabre_command`. Commands are limited to submitting work within the grant's limits, answering clarification questions and cancelling the grant's own runs. Delegated runs cannot publish a pull request, change dependencies or approve architecture; permission, architecture, scope and exception decisions, budgets and security exceptions stay with the owner in the console. Each command is recorded against its grant.

SABRE publishes the API on loopback only. Reach it remotely through a tunnel that terminates TLS and authenticates the network path (for example a private mesh VPN); do not publish the port to the internet.

## GitHub and project gates

Register a repository HTTPS URL and explicit argv arrays for its gate commands. A repository needs an initialized default branch. CREATE requires a prepared repository or an explicit owner step to create one. For example, stdlib-only Python fixtures can use `["python", "-m", "unittest", "discover"]`; Node fixtures can use `["node", "--test"]`.

The executor prepares dependencies only from supported locked inputs in an isolated preparation environment. Missing or unsupported lockfiles cause an actionable block. Code execution and final gates have no network. Changes requiring a broader dependency or network policy are owner decisions.

Verification runs the project's deterministic gates first, against the exact snapshot. A failed gate decides the repair without a model QA call; otherwise model QA receives the gate commands, exit codes, output digests and bounded output tails as evidence and only runs further approved checks when they add evidence. QA runs those commands on disposable copies of the source snapshot, so builds cannot add generated files to the delivery workspace. The developer removes its own untracked build outputs before handoff. SABRE records the final gate separately against the exact delivery snapshot.

Publication uses GitHub's Git APIs outside coding containers. Before updating a branch it checks the base commit, snapshot, gates, review and security result. The branch and PR receipt allow recovery after a lost response. Branch conflicts remain unresolved until inspected; the system does not force-push.

New deliveries use `feat/sabre-<work-id>/r<revision>` for CREATE, `fix/` for PATCH and `chore/` for MAINTAIN, with the corresponding Conventional Commit type. A previously recorded publication keeps its original branch when resumed, including the legacy `sabre/` prefix. Its stored request hash must still match the repository and commit; changing those inputs blocks recovery instead of creating another PR.

## Security decisions

Daily watch records prioritized remediation proposals in its work order; it never starts those development tasks. It runs for every registered project at 08:00 UTC, calls no model, and its record appears in Runs as Monitoring, not as a run: it counts as no delivery and offers no pause or resume. The newest review of a project is the current one. Earlier ones are kept and open by their address, but the run list, the attention inbox and Security findings leave them out, so a review that could not finish asks for attention only until the next one runs, and a finding is listed once, not once per day. Scanner failures and secrets block review. New high/critical findings block delivery unless the owner explicitly accepts that exact risk.

In a paused or blocked development order, review the finding and use the panel, or file the request over MCP with `sabre_approve_security_exception` and confirm it in the console, with its fingerprint, justification, future expiry (at most thirty days), snapshot digest, rules version and plan revision. Then resume the order for a new security review. Secrets and incomplete scanners cannot be waived. `sabre_security_exceptions` lists the audit history; `sabre_revoke_security_exception` revokes an approval at a safe boundary. No specialist or autonomous Slack tool can grant an exception.

Changing the source, rules, plan or active exception policy invalidates the approval. The publisher checks expiry immediately before each external write. Revocation does not undo an already published PR.

## Pause, failures and recovery

Pause stops at a safe execution boundary and preserves checkpoints. Resume reuses the work id and its pinned graph. Cancel does not claim to undo an external effect that already happened. A scope change requires paused or blocked work; it increments the plan revision, replaces its task plan and invalidates earlier evidence. Its receipt records the new paused revision without preparing the repository inside the HTTP/MCP request. Resume reconciles that revision into LangGraph before the worker resets and prepares the workspace. This resolves the repository's current base again and discards the previous workspace, so inspect pending changes before revising scope. Historical checkpoints and accumulated usage, including unknown reservations, remain intact. After a lost response, query the revision before repeating the command.

The queue detects stalled workers using heartbeats and retries their pending jobs. It keeps the jobs still to do and the ones that failed; a job that succeeded is deleted when it finishes, because what it did is recorded in the run, its events or the delivered notification, and the two maintenance tasks alone finish 2,880 times a day. A resumed LangGraph run continues from its checkpoint. Provider calls and external writes have separate usage/effect accounting because restoring a checkpoint does not undo them.

The executor persists snapshots as UID 0 with all runtime capabilities removed. `up` provisions its own `executor-state` volume with a root-owned private directory. It repairs the previous image's directory ownership using an isolated, networkless helper with only `CHOWN`; it does not change existing files recursively or grant capabilities to the executor. Unknown volume ownership or incompatible entries stop startup for explicit recovery. After correcting a snapshot persistence failure, resume the existing work id. If intake never saved a source snapshot, that retry resolves the repository's current base again.

Back up both PostgreSQL databases and the artifact/broker snapshot volumes while the application is quiesced. Keep bootstrap/master material separately in an owner-controlled protected destination. Encrypted database backups alone cannot restore secrets without the master key. Restore the databases and volumes together with the same application image and configuration; validate a pending HITL question, its source artifacts and vault decryption before reopening access. Infrastructure commands must never remove a shared volume or owner resource by image name or broad prune.

`node infra/backup.mjs backup` creates a versioned archive under `work/backups`; `verify <path>` restores a scratch instance and validates it. Format 2 includes `vault.sql` with encrypted secret values. Bootstrap/master files remain in their protected volumes and are not exported into that archive; separately preserving them is an owner operation. `restore <path> --replace` explicitly replaces this factory's data and requires a reviewed recovery destination. A verification that reuses the original master proves database recovery, not recovery from loss of the master volume.

## Verification

`node infra/dev.mjs test`, `lint` and `types` run the backend toolchain in pinned containers. Set `SABRE_DEV_NETWORK=sabre-factory_control` and run `node infra/dev.mjs test tests integration` for the required PostgreSQL checks. In `web/`, run `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build`.

PostgreSQL checks create private, disposable databases and bootstrap files per invocation. `node infra/bootstrap-check.mjs` verifies repeatable provisioning and encrypted legacy import. After starting the factory, `node infra/runtime-check.mjs` checks authentication, MCP and the absence of raw credential environment fields without printing values. It also runs the executor's acceptance script inside the deployed executor, through its Docker permission proxy and with a workspace of its own that it removes: a sandbox command must find no network, no Docker socket, no broker state and no credential, a gate must run against the snapshot it names, and a restarted broker must restore the workspace. It touches no run and adds about half a minute to a check that takes about one. `node infra/qa.mjs up|open|check|refresh|restart|down` operates a separate browser fixture on loopback port 8001 with a random owner credential generated per fixture and kept in its bootstrap volume; `open` pairs a browser with it. It uses its own publishing network instead of joining the production outbound network, never configures a real provider and never reuses the production master.

`node infra/qa.mjs check` runs the browser journeys of `web/e2e-real` against that fixture: the console as the application serves it, the real API and a real PostgreSQL, on a desktop and a phone viewport. The other browser suite (`pnpm test:browser`) answers every request from a mock, so it cannot see a contract the console and the API understand differently; this one can, and it fails on any request the application refuses or fails, any uncaught exception and any error written to the console. It pairs a browser with a one-use link that reaches the test process through its environment, never as an argument or a printed line, and signs it out when it finishes. It refuses to run when the fixture serves a console build other than the one in the working tree: run `sabre build api`, then `node infra/qa.mjs refresh`. The fixture has no model provider and no worker, and no journey launches a run: what it proves is the console and the API together, not the factory doing work.

Real-provider, real Slack and desktop-client connection checks require the owner's integration setup. Unit or mocked HTTP tests are not evidence that those live integrations are configured.

## Agent loop

Each developer task carries its planned scope, acceptance criteria and registered verification commands in `task_context.task`; QA and review see the acceptance of completed tasks. A routine tool failure (invalid arguments, stale digest, missing file or range, edit count mismatch, a timed-out command) returns to the model as an error observation, at most eight times per agent step, with no effect performed. Authorization, policy, secret, budget and infrastructure errors still stop the stage. A model turn without the required structured result, or with a tool request outside the contract, gets one corrective retry on the same checkpoint thread. Tool results are bounded: `read_file` returns up to 32 KiB at a line boundary with a digest and the line to continue from, `list_files` up to 500 paths, and command output keeps its first 4 KiB and last 12 KiB with the full output stored as an artifact. Repair feedback lists failed gates with their output tails, then blocking security findings (at most 20, without remediation text), then bounded QA and review summaries.

Agents are asked to request independent tool calls together; `read_files` reads up to eight files (48 KiB in total) in one call and reports a missing file without discarding the others. `read_context` recovers archived reads in pages of 8,192 characters. The executor serves file reads, listings and snapshots from the verified snapshot it records after every workspace change, so a read no longer starts helper containers; any mutation drops that view first, and a failed save or an executor restart falls back to the helper. Deterministic gates and security scans still check the actual workspace bytes. CLI prompts embed SABRE's own JSON messages as JSON values (`content_json`) instead of escaped strings; tool results stay verbatim because edits depend on their exact bytes.

Each agent step and repair attempt starts from a fresh conversation, so specialists keep bounded working notes with `record_note`: file roles, commands that pass or fail, decisions and dead ends. A note holds at most 1,000 characters; an assignment (a planned task, or the stage role when there is no task) holds at most 24 notes and 8 KiB. A full notebook rejects the note with a recoverable `WORK_NOTES_FULL` error asking the agent to consolidate: it records one shorter note listing the older note ids in `replaces`. Secrets are blocked before recording and notes are redacted again when injected. Notes live in the factory checkpoint (`work_notes`, per plan revision) and are rebuilt from the agent's own checkpointed tool calls when a stage resumes before committing them. Later procedure steps and repair attempts of the same assignment receive them as `work_notes`, labelled as the agent's own untrusted, possibly stale observations; notes never cross to another task. The work audit counts accepted notes per agent.

The Supervisor relays owner decisions but cannot compose them: answering a permission, architecture, scope or exception question requires the answer to appear in the owner's own message.

## SABRE Bench

`sabre bench` (or `node bin/sabre.mjs bench [--task <id>]`) runs the harness bench in the development image with no network and no model provider. It drives the real factory graph, agent loop, tool policies, context projection, budget reservation and checkpoints over the fixture repositories in `backend/bench/repos`. Only the language model is replaced, by a reference policy that inspects, edits and verifies the way a competent agent would. Each task in `backend/bench/tasks` has a deterministic grader: hidden tests run against the delivered snapshot for PATCH tasks; AUDIT tasks require an unchanged source and a report naming the expected paths and risks.

The JSON report is saved under `work/bench/`. Per task it records the outcome and grade, model calls by role, estimated and reserved tokens, sent context bytes, tool calls, result sizes and time, the completed stages and the action order. Tokens are estimated as UTF-8 bytes divided by four because no provider is called; they are comparable between bench runs, not with provider invoices. `probes` describe harness behaviour (whether the developer receives the task's scope and acceptance, whether deterministic gates run before model QA and reach it, and whether a developer repair attempt receives its earlier work notes; `patch-discount-repair` makes a failing first attempt that only a repair attempt with that note can correct) and `budget_feasibility` says whether one call at the configured context ceiling can be reserved under the default token budget. Probes describe; they do not grade. `context.recoveries` counts the tool calls an agent made only to see again what it had already read, and `context.prefix` says, for the turns that have a previous request, how many rewrote an earlier message (a compaction batch) and how much of the previous request the others kept. `audit-ledger` reads six modules over three turns and fits its window; `audit-ledger-full` reads sixteen and has to compact.

The bench therefore measures the harness, not model quality. A bench pass is not evidence that a real model completes these tasks; that requires a real-provider run under an explicit owner budget. Keep the bench green before and after every harness change.

`sabre bench compare` runs the suite and sets what the harness did against the baseline committed in `backend/bench/reports/baseline.json`. The baseline holds the mechanics of a run without its timing: verdicts, probes, model calls and estimated tokens by role, sent bytes, tool calls and failures, stages, and the derived tokens per call, recovery ratio and share of tokens by specialist. It holds no prompt and no code, and two runs of the same commit produce the same file. A regression is something that got worse: a task that no longer passes, a probe that turned off, more model calls or tool failures, or a cost that grew by more than 2%. It exits with 1. Any other difference is a change: not worse, but the baseline no longer describes the harness. Record it again with `sabre bench baseline`, in the same change that caused it; `sabre bench compare --strict` also fails on a change, which is the form for CI.

## Per-call telemetry

Each model call records its reservation, the provider-reported input and output tokens, the input tokens read from the provider's cache and those written to it, the sent and original context bytes and the time from reservation to settlement. A call that never settled keeps its reservation and records why it failed (rate limit, overloaded, timeout, authentication, invalid request or other) when the factory saw the failure. Agent and tool boundaries record their measured duration, and tool completions record the size of the result handed back to the model, never its content. The run's Activity view shows tool time and a per-call table; the audit API (`GET /api/v1/work/{id}/audit`) returns the same fields as `calls` and `tool_timings`. Calls and runs recorded before this measurement report these values as unknown.

## Traces and logs

`sabre up --traces` starts the bundled Jaeger (http://127.0.0.1:16686, loopback only), points the API, the worker and the executor at it and sets the address a trace opens at. Without the flag, the next `sabre up` runs the services without an endpoint again unless `SABRE_OTLP_ENDPOINT` is configured. Any OTLP backend can replace Jaeger: set `SABRE_OTLP_ENDPOINT` and, to keep the links, `SABRE_TRACE_VIEWER_URL`.

Spans exist for a run's execution, its stages, its specialists, their model calls and tool calls, and each command the executor runs. They carry the factory's `sabre.*` attributes and, beside them, the OpenTelemetry GenAI names (pinned to one commit of those conventions while they are in development), so a backend that understands GenAI telemetry reads tokens, models, tools and the conversation without a mapping. No prompt, response, code, command, argument or output is exported, and there is no switch that turns that on. A paused or blocked run continues in a new trace that links to the previous one. In the run inspector, the Trace tab opens a step's trace in the viewer when an address is set and shows the identifiers as text otherwise.

The API, the worker and the executor write one JSON line on standard error (`sabre logs`) for an admitted run (`work.admitted`), each stage change (`stage.started`, `stage.completed`, `stage.failed`, `stage.interrupted`), each failed model call (`model.failed`), each executor failure (`executor.failed`) and each owner decision (`owner.answer`, `owner.control`, `owner.budget`, `owner.scope`, `owner.security_exception`, `owner.confirmation`). A line holds a time, the event, identifiers (run, project, invocation, phase, role), codes (decision, failure class, error code), counts and the trace it belongs to; anything else is left out, so no message, answer or command can appear in it.

## Figures across runs

Runs → Insights reads `GET /api/v1/metrics/runs?days=30` (optionally `mode=create|patch|maintain|audit` and `project_id=`). The window is whole UTC days, today included, up to 365. Nothing is stored for it: each answer is a sum over the usage ledger and the event log, so it always agrees with what each run's audit shows. It reports runs by outcome (completed, stopped, cancelled, waiting, active), model calls settled and not with the failures by class, measured tokens and their split by kind, the cost charged through API prices, active time, the medians per completed run, the share of input read from cache, and the recovery ratio (tool calls that paged back archived text, over all tool calls), in total, by flow, by specialist and by day. Internal security-watch work orders are not runs and are left out.

A CLI session is not charged per token, so its calls add nothing to the API cost. The Claude CLI does report what each call cost at API rates; that figure is kept as reported (`reported_cost_usd`) and shown under its own name, never as a charge. It is the session's own estimate, not an invoice.

A figure that nothing measured is `null` and reads Unknown in the console, never zero: calls through a CLI session have no price per token, a call that never settled has no token count, a provider that reported no split has no cache share, and a window with no completed run has no median. At most the newest 5,000 runs of a window are counted; `truncated` says when that bound was reached.

## Annotated evaluation

Run the deterministic evaluator from the backend's Python 3.14 environment, using `SABRE_BOOTSTRAP_FILE` or `--bootstrap-file` to read owner authentication from a protected control file. Do not inject a raw token into the environment. It performs authenticated GET requests and needs no master-key mount or model access:

```sh
python -m sabre.evaluation --cases work/evaluation-cases.json --api-url http://127.0.0.1:8000 --output work/evaluation-report.json
```

Both paths must be available inside that runtime. `SABRE_API_URL` supplies the API URL when the option is omitted. HTTPS endpoints and the local/API service HTTP addresses are supported; redirects and credentials embedded in URLs are rejected.

The input is `{"schema_version":1,"cases":[...]}`. Each case identifies a unique real `work_id` and `case_id`. Annotate `expected_outcome` as `complete`, `block` or `unknown`, and `functional_verdict` as `pass`, `fail`, `unknown` or `not_applicable` (the last is for expected blocks). Known annotations require `label_source`, an independent test/review reference, and `expected_plan_revision`. Functional pass/fail also requires `reference_commit` matching the order's delivery evidence. Read these identifiers from the API; do not substitute a fixture id, assume the current revision, or treat `completed` as an independent functional verdict. Missing judgments remain unknown. Stale revision/commit annotations are not scored.

Use separately annotated Python and JS/TS orders for CREATE, MAINTAIN and PATCH. Read-only `security_watch` reports are not development deliveries; including one yields `NON_DELIVERY_REPORT` and an incomplete observation. The evaluator does not create orders, execute project code or fabricate a benchmark result. Reference annotations must come from the acceptance oracle or an independent review of the actual change.

A false approval is a completed order whose annotation expected a block or found functional failure. An incorrect block is a BLOCKED/FAILED order annotated to complete; queued, running, HITL, paused and cancelled orders remain incomplete. Every rate includes its assessed and unknown counts; no eligible observations produce `null`, not a zero failure rate. The report preserves the API's calls, tokens and recorded USD, which may include retained reservations and are not a provider invoice. `elapsed_total_seconds` is the recorded `updated_at - created_at` interval, including waits until that observation; `active_seconds` is the separate recorded active time. Completed-latency aggregates include completed orders only.

Exit codes are `0` for a complete evaluation without known false approvals/incorrect blocks, `1` when either is observed, and `2` for incomplete observations, missing judgments or input/access errors. A known failure still exits `1` when other cases are incomplete. Reports contain identifiers, annotation provenance and measurements, not objectives, repository contents or provider error bodies.

## Candidate distribution

After committing the reviewed candidate, export production web licenses with `pnpm --dir web licenses list --json --prod > work/web-licenses.json`, build the development image from that checkout, then run `node infra/release.mjs`. It produces a clean Git source archive, backend and web CycloneDX inventories, a source receipt and SHA-256 checksums under ignored `work/release/`. The source receipt is not a cryptographic attestation. CI retains artifacts tied to the exact commit. Public push builds additionally use GitHub artifact attestations; private attestations require GitHub Enterprise Cloud and are not provisioned implicitly. See [GitHub attestation requirements](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations).

For a registered project, `/api/v1/releases` prepares an immutable candidate from a completed delivery's retained checked source: native archive, versioned changelog, lock-derived dependency inventory, source receipt and checksums. Preparation does not publish. Review its exact digest and named CI checks, then separately authorize publication for that candidate and revision. Current protected-branch check contexts, all check-run conclusions and combined commit statuses must match the exact commit; security, artifact SHA-256 values and the tag are rechecked before external effects. The existing GitHub publish credential also needs access to these CI and protection reads. Unknown create, upload or final-publication responses use the same durable candidate receipt and read-only reconciliation; changing a client key cannot create another release. Mocked tests are not release evidence, and candidates from synthetic runs must not be published. This operation grants neither merge nor deployment.

Before making a release public, review both inventories and pinned binary notices, scan the exact images and archive, verify checksums, and complete installation, flow execution, stop/restart and restore on every advertised host. Keep the repository private while a gate lacks evidence. The backup archive excludes the master key and bootstrap volumes: retain those protected volumes and the exact referenced database/application images separately. The launcher retains previous built images when updating local tags; do not prune them while they support a retained backup.

The control runtime excludes pip, its bundled installer and dependency download caches; managed project installation belongs to the isolated language runners. Debian-based application, database and language images explicitly install APT 2.6.2 to address [CVE-2026-109518](https://security-tracker.debian.org/tracker/CVE-2026-109518). This security fix overrides the ordinary seven-day dependency delay; vulnerable APT retries are disabled while installing it. Base-image advisories still require candidate-specific review, including advisories without a distribution fix. A passing source-lockfile scan does not clear image findings.
